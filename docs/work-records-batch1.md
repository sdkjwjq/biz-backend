# 工作纪实第一批：数据、权限与统计

## 本批交付边界

本批提供独立表、迁移与回滚脚本、登录保护、填报资格、月度唯一草稿、读取列表和详情、统计预览、版本化刷新及快照读取基础。

**尚未交付**页面、正文编辑与提交接口、Word 导出。按计划在本批审核通过后实施第二批；不把测试中模拟的已提交数据视为完成了提交功能。

现有本地业务库不执行迁移，不重启本地测试服务。当前接口使用隔离数据库验证；后续部署须先执行迁移。

## 权限

- 年度填报资格：`biz_task.level=3`、未删除、年度为2025—2029，`auditor_id` 等于当前账号。一级任务负责人或 `role=2` 本身不授予填报权限。
- 活跃填报人可查阅所有已提交纪实。管理员 `role=0` 及配置的指定账号可全校查阅并具备后续导出资格。
- `work-records.viewer-user-ids`：逗号分隔账号ID，默认空。可通过部署配置或 `WORK_RECORDS_VIEWER_USER_IDS` 设置；无须修改账号原角色。名单配置错误会阻止启动，避免静默扩大授权。
- 非本人草稿对管理员、指定查阅账号和其它填报人均不可见。
- 资格撤销后本人历史已提交记录仍可查阅；本人草稿可查看但不能刷新，全校查阅资格同步失效。
- 全部身份读取当前数据库账号，接口不接受客户端指定填报人身份。新路由加入现有 JWT、删除账号和强制改密拦截。

## 数据结构

迁移：`scripts/work-records/001_work_records.sql`，回滚：同目录 `001_work_records_rollback.sql`。

- `biz_work_record`：填报人姓名与账号、年月、状态、版本、三段正文、创建和提交时间；`owner_id+record_year+record_month` 唯一。
- `biz_work_record_entry`：预留一级改革任务、顺序及三段文字，单份纪实内改革任务不重复。第二批接入正文保存。
- `biz_work_record_snapshot`：每份纪实一个版本化 JSON 统计快照，保存生成及截止时间、任务及改革目录、完成数量和核实提示。刷新草稿替换快照；已提交快照不得刷新。
- 草稿状态 `0`，已提交状态 `1`；版本自 `0` 起，成功刷新递增。外键只关联新增表，不关联可变化的任务目录，保留历史快照。

## 第一批接口

以下路径均位于 `/api`，使用现有 Authorization 登录 Token：

| 接口 | 行为 |
| --- | --- |
| `GET /work-records/capabilities` | 返回可填报年度、是否可创建、全校查阅、导出资格及本人历史记录标志 |
| `GET /work-records/statistics?year=2026&month=1` | 仅预览本人的指定年月统计，不写入业务数据 |
| `POST /work-records` | 请求 `{ "year":2026, "month":1 }`；新建本人草稿及初始快照，已有记录直接返回 |
| `GET /work-records` | 支持 year、month、ownerId、status、page、pageSize；默认20条，最多100条，返回 total 和 records |
| `GET /work-records/{id}` | 返回 record、statistics、editable，跨权限不可见记录统一404 |
| `POST /work-records/{id}/statistics/refresh` | 请求 `{ "version":0 }`；重新核验资格，事务内更新版本和快照，不修改正文 |

所有年月必须为整数，不接受小数自动取整或字符串强制转换。未来月份返回400，资格不足403，版本冲突或已提交409，错误体沿用 ErrorVO。客户端提供 ownerId 不能改变新建归属。

## 统计口径及历史限制

- 全年分母来自生成时该账号负责审核的全部有效三级任务，年度按 `phase`；不受文字填报项目选择影响。
- 历史月份截止到上海时区月末，当月截止到生成时刻；0任务的完成率为null，前端应显示“—”。
- 完成证据使用三级审核单填报值达到当前配置目标，且有 `post_status=40` 的真实归档日志。取首次可证明达标归档时间，多次日志或重提不重复计数。
- 四级批量填报现有流程会在三级任务留下汇总审核单，直接读取其汇总值，不逐个四级任务计数。
- 对只有旧四级归档记录、没有三级汇总证据的历史任务，明确列为待核实，不根据今天的四级值反算历史月份。
- 已替换材料的软删除审核单，只要归档证据保留仍可核实；不能用删除标志抹掉真实历史。
- 当前已完成但缺少归档时间／填报值、目标无效、快照说明此前已完成而首次归档证据缺失等情况，输出核实原因，不把后续重提月份冒充首次完成月份。
- 明细审核状态按截止时间内的审核日志展示。任务归属及目标没有完整历史版本，固定标注“采用生成时的年度任务配置”。
- 新建并发通过数据库唯一约束归并为同一记录；读取重复新建结果不覆盖已有快照。刷新按版本和草稿状态原子更新，快照保存失败时一并回滚版本。

## 验证与运维

验收结果：新增12项真实 HTTP/MySQL 测试、既有42项隔离回归全部通过，失败及错误为0；Java编译通过，本批文件 `git diff --cached --check` 通过。结果摘要见 `docs/evidence/work-records-batch1/`，不保存包含登录凭据的完整请求日志。两个随机数据库均已清理。

工作纪实隔离测试：设置 `SHUANGGAO_TEST_DB_PASSWORD` 后运行 `python scripts/run-work-record-regression.py`。

脚本仅复制本地业务库的结构，创建随机 `biz_review_test_*` 数据库，执行正向迁移、回滚、再次迁移，然后运行真实 HTTP/MySQL 测试，最终删除随机数据库。自动定时任务在测试中关闭；所有账号及任务均为合成数据。

故障回滚测试会故意注入数据库触发器失败，因此日志中的预期500不表示测试失败，以 JUnit 汇总为准。测试使用SQL模拟已提交状态，仅验证本批的读取权限和冻结保护；第二批将通过真实提交接口补齐验证。

完整部署顺序：迁移 → 后端 → 前端。本批正向脚本应只执行一次，重复执行会报表已存在；部分执行失败时先检查已存在表结构，不自动删除已有数据。回滚应先恢复旧应用，保留或备份新增表；只有确认不再需要纪实数据后，才执行会删表的回滚 SQL。

已有未提交日志、旧测试和前端修改不纳入本批提交。当前没有页面，所以第一批不声称已完成 Playwright 验收；页面测试在第二批进行。
