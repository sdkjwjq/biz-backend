# 失效审核通知清理与 r4 更新包

## 行为

- 任务、绩效、成果的待审核通知，只有对应业务仍有效、处于待审核阶段且接收人仍为当前处理人时保留。
- 审核流转、退回、撤回时，在原事务内逻辑删除失效通知；列表读取也按当前业务状态过滤。保留结果通知、督办、月度通知和全部审核记录。
- 任务通知只关联任务 ID，因此任一有效审核仍待该接收人处理时保留，不推测关联到某一历史审核单。
- 新任务通知补齐删除标记和创建时间，避免空标记影响已读操作。
- 普通查询先筛选通知 ID，再更新这些 ID，避免带业务子查询的 UPDATE 在并发提交时引入额外共享锁。
- 运行时与更新包共用 `src/main/resources/sql/stale-review-notices.sql`，避免历史清理和页面显示规则不一致。

- Playwright：8 项通过，含消息列表、未读数量、真实待办跳转、已处理只读、非当前处理人只读、无权限访问；延迟与失败响应采用注入模拟。
- 更新包：15 组检查通过，包括真实打包 JAR 启动、增量迁移、重复迁移、清理只改通知标记、幂等执行、单独恢复删除标记、失败回滚。Linux 进程管理在 Windows 上通过模拟验证，未远程执行生产更新。
- 前端构建、后端打包、修改文件静态检查通过。前端仍有既有大资源包提示。
- 线上备份的本地副本：清理前完整备份，清理 281 条任务、71 条成果提醒；管理员涉及 80 条，清理后消息接口返回 5 条有效消息。本次数量不代表当前线上数量，部署时重新计算。
- 隔离测试库和服务已清理；保留 `biz_debug_20260920`、5175/18082 本地调试服务。真实备份及本地调试资料未提交 Git。

## 部署与回滚

上传 `releases/shuanggao-update-20260920-r4` 到 `/root/biz-backend/`，运行 `bash update.sh --update`。不要添加 `--restore-backup`；本次不恢复旧数据。

先备份数据库和文件，再补结构及清理通知，最后替换 JAR、前端和模板。清理范围及恢复说明见包内 README。更新失败会恢复应用及本次通知删除标记；普通应用回滚保留清理结果。必要时可使用本次备份目录中的 `restore-notice-flags.sql` 恢复通知标记，无需整库恢复。

包中包含此前授权携带的私有历史备份，仅允许存放 root 私有目录。更新脚本不把 MySQL 密码写入包内或命令行。
