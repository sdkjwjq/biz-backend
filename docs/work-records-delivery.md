# 工作纪实完整交付

## 已实现

1. 年度任务 `auditor_id` 填报资格、每人每月一份、草稿私有及已提交查阅权限。
2. 独立菜单、年月／填报人／状态筛选、五部分填报、300字限制、未保存提醒和版本冲突保护。
3. 提交重新计算并冻结任务范围、统计及文字；已提交不可修改；历史证据不足明确标注待核实。
4. 管理员及配置的指定账号可在列表单份导出、跨页勾选合并导出，也可在只读详情导出。切换筛选清空勾选，避免混入上个筛选结果。

普通填报人具备查阅资格，不自动具备导出资格。首期没有审批、上传附件、撤回或提交后修改功能。

## Word 模板与接口

使用客户 `docs/工作纪实导出模板20260527.docx` 制作资源模板 `src/main/resources/templates/work-record.docx`，原文件未修改。`scripts/work-records/prepare-template.py` 可重建资源模板（需要本机 python-docx，仅开发工具，不是服务运行依赖）。

保留原封面、五部分结构、两张表的布局，替换年月、填报人、导出日期。删除说明、示例及空白占位行；未实际填文字的改革任务不导出。关键进展和典型做法在同一单元格分别标注，阶段性成果独立列。任务其它列留空。

`POST /api/work-records/export`，请求示例 `{"ids":[1,2]}`，使用原 Authorization 登录凭据。单份和批量共用接口，编号严格为正整数；重复编号去重。后端按年度、月份、填报人账号排序，逐份分页合并，不跨人汇总统计。

导出前在一致性事务中校验全部记录的权限和提交状态，任何记录缺失、无权限或为草稿均整批拒绝，不静默跳过。内容只读取已提交快照，修改当前任务、目标或姓名不影响历史内容。导出日期是本次日期，统计生成／截止日期来自冻结快照。

成功返回 DOCX 二进制、附件文件名和 `Cache-Control: no-store`；错误仍返回现有 ErrorVO。前端请求工具只增加可选 `responseType: 'blob'`，原 JSON 调用不变，认证错误仍沿用原有处理。

## 部署顺序

1. 备份现有数据库与应用产物；检查纪实三表是否已存在。尚未部署第一批时执行 `001_work_records.sql`，仅执行一次；已部署者不用重跑。本次没有其他迁移，不改变原任务及审批数据。
2. 部署后端JAR，沿用原有JDK17、数据库和文件目录配置。指定查阅导出账号设置 `work-records.viewer-user-ids=账号1,账号2`，或环境变量 `WORK_RECORDS_VIEWER_USER_IDS`，默认空；管理员默认可导出。
3. 部署前端文件，保留服务器原有API反向代理和上传目录设置，不覆盖基础设施或密钥。
4. 用具备年度任务auditor资格的账号检查草稿创建、保存和提交；管理员检查查阅和Word下载。指定账号名单待客户提供后补充配置。
