## 19-1【高 / BUG】任务通过与退回同时成功

- 位置：`service/BizService.java:758`、`:1630`、`:1396`。
- 同一待审任务并发发送通过、退回，两次实际 HTTP 均成功，新增两条原状态均为 10 的日志，分别进入 20 和 -10。本次最终为退回，任务实际值从 3 恢复为 0。
- 原因：审核状态使用普通查询读取，更新时没有锁定或原状态条件，两个请求均基于旧状态执行。
- 影响：成功提示与最终结果可能冲突，重复推进和退回会产生矛盾流程记录。
- 建议：统一审核与撤回等竞争操作的锁定顺序，在事务内读取最新审核状态并校验；只有成功推进者写日志和通知。沿用原业务状态码。

## 19-2【中 / BUG】绩效同一审核阶段重复通过

- 位置：`service/PerformanceService.java:580`、`:623`；`mapper/PerformanceMapper.java:110`。
- 同一专业群待审单并发执行两次通过，两次均返回“待完结归档”，保存两条 10→20 的 pass 日志，管理员收到两条相同归档待办通知。
- 影响：同一阶段重复处理，审核轨迹及通知重复。此例没有跨阶段，也没有证明重复归档。
- 建议：事务内锁定审核单，取得最新状态后重新核对处理人与阶段；重复请求应拒绝或按幂等规则返回，不重复写入。
- 补充边界：初次通过＋退回测试触发一次数据库死锁及一条成功退回，不将其描述为两者均成功。本项最终证据仅为重复通过。

## 19-3【高 / BUG】在途绩效撤回覆盖已完成归档

- 位置：`service/PerformanceService.java:667`、`:678`、`:682`，关联归档分支 `:641`。
- 提交实际值 3 并通过专业群审核后，提交人发起撤回。暂时锁定年度值行，使撤回读取阶段 20 后停在恢复数值；管理员此时归档成功，随后放行撤回，撤回也成功。
- 最终审核单变为状态 0、逻辑删除 1，年度实际值恢复 0，但“已完结归档”通知和 20→30 日志已存在，另有一条基于旧状态的 20→0 撤回日志。
- 影响：管理员已经完成的归档被在途撤回覆盖，归档结果、绩效数值和通知矛盾。串行情况下原代码禁止撤回状态 ≥30，本例绕过了该已有校验。
- 建议：审核与撤回共同锁定同一审核单，统一锁顺序；撤回取得锁后重新检查当前状态，再恢复快照。与 19-2 一并设计并发保护，避免只修审核入口。
