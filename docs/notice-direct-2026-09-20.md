# 消息中心进入任务审核等待过久

## 复现与结果

按用户要求将提供的 `data/20260920backup.sql` 完整导入本地独立数据库 `biz_debug_20260920`，补齐当前数据库结构。未覆盖原 `biz`，未连接或修改生产服务器。管理员账号 110228 复现了第一条未读通知指向审核单 241、任务 587 的情况。

同一通知进入同一审核单的本地浏览器实测：修复前 12140ms / 849 个请求（595 个任务历史查询、233 个附件请求）；修复后 1312ms / 13 个请求（1 个任务历史查询、0 个附件请求）。这是本机对比，不承诺线上网络耗时相同。

该审核单实际已归档；通知的未读状态与业务处理状态独立，不能据“未读”推断仍需审核。

## 修复

- 任务通知直接读取对应任务及其审核单，不为定位单条通知切换历史标签、遍历全校任务。
- 依据后端当前用户待办决定能否审批；本人待办可处理，历史及其他处理人记录只读，并给出明确提示。
- 优先使用审核接口返回的文件名称；列表不再为每条记录预读附件。单个详情缺少名称时后台补读，不阻塞弹窗。
- 保留既有权限接口及写入流程，处理快速跳转、卸载、失败后的加载状态。
- 原通知只有任务 ID，没有审核单 ID；沿用任务级定位，优先本人有效待办，否则最新有效记录。不虚构历史通知与单据的精确关联。
- 手动切换到完整“审批记录”仍沿用原有历史列表接口，本次重点解决通知定位等待及列表批量附件读取。
