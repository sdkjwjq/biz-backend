# 强制改密与线上字段对齐

## 已确认规则

- 以 `sys_user.force_password_change` 为唯一强制改密依据：1 要求改密，0 不要求。不再以密码强度判断是否完成首次改密，也不将该字段解释为登录记录。
- 标记为 1 的有效账号可使用工号或当前密码登录，获得的会话只能改密、查询改密状态或退出；管理员也遵守此规则。刷新及旧 Token 均重新核对数据库标记。
- 成功修改密码或登录页重置密码，在同一条更新中保存新密码并将标记置 0。新密码仍须至少 8 位、包含大写字母、小写字母和数字。
- 用户明确选择：所有有效账号，包括管理员及标记已为 0 的账号，都可在登录页“原密码或工号”中填写自己的工号重置密码；原密码验证方式继续可用。此入口按已确认需求不附加身份核验。
- 标记清除后工号不再是备用登录密码；重置后使用新密码登录，不自动登录。不改变已有会话有效期。
- 新建账号明确写入标记 1，不依赖线上默认值 0；普通资料修改不改写标记。
- 专用密码更新只修改密码、改密标记及更新时间，不覆盖用户资料；以读取时密码作为原子更新条件，防止同时通过旧密码验证的请求覆盖新密码。工号可再次发起新一轮重置属于本次明确确认的行为。

- `scripts/ui-audit/password-flag.cjs`：5 组检查通过，包含迁移连续执行仍保留所有合成账号密码及标记；管理员/普通账号各自真实首次登录、刷新后弹窗、成功改密、标记清除，以及已改密后工号重置、重复点击和新密码重新登录。未捕获浏览器运行异常。
- 修改文件 ESLint、前端生产构建及后端打包通过。前端仍有原有的大文件体积提示。
- 测试仅用随机隔离数据库、合成账号，不导入线上个人资料和密码。证据在 `target/ui-audit/evidence-password-flag/`。

## 部署及备份恢复安排

1. 下次更新按用户明确要求，使用本地 `data/20260920backup.sql` 作为线上数据恢复来源。本次仅检查其中表结构，**未恢复该备份、未修改线上数据**。备份文件包含敏感数据，不提交 Git。
2. 实际恢复前停止业务写入，另行完整备份更新时的线上数据库、材料和程序，并保留恢复之后需要核对的数据。恢复旧备份是独立且显式的数据恢复步骤，不应混进普通增量更新脚本；它会让相应表回到备份时点。
3. 恢复后按最终应用版本补齐全部增量迁移（包括工作纪实及删除功能），再启动应用。本次脚本为 `scripts/password/001_force_password_change.sql`：线上已有字段时完全不更新密码、标记或字段默认值；没有字段的环境才新增，现有账号要求首次改密。
4. 先迁移、后端、前端。旧发布目录 `releases/shuanggao-update-20260920` 尚未重组，不包含本次修改，也不会自动恢复上述备份。正式发布继续使用去除本地密码的发布构建及服务器外部配置。

## 回滚

用对应 Git 反向提交或备份应用恢复代码；保留 `force_password_change` 列及已有值，不删除线上既有字段，不回填旧密码。回退至密码强度判断版本会重新产生本次线上状态不一致问题，优先使用修正版本。不提供删除该线上字段的回滚 SQL。
