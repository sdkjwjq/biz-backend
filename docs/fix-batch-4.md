# 第四批后端修复记录

本批按用户确认修复第 1、4 项；第 2 项预算金额解析、第 3 项预算锁定后导入覆盖按忽略处理。

## 1. 审批结果不能为空

- 问题：绩效和成果审批将缺失的 `is_pass` 当成 `false`，无明确决定的请求也会退回审核单，并恢复绩效实际值。
- 改动：在两个 Service 入口增加非空校验，返回现有 `ErrorVO` 格式的“审核结果不能为空”；显式 `true` / `false` 保持原流程。
- 闭环：真实 HTTP 请求复现了绩效值恢复、成果状态退回。修复后覆盖字段缺失和显式 `null`，校验业务表、快照、日志、通知全部不变；正常通过和退回仍可执行，绩效覆盖两个待审阶段。
- 验证：隔离 MySQL 库累计 17 项回归通过，0 失败、0 错误、0 跳过。

## 4. 并发重复提交

- 复现：通过测试专用 MyBatis 拦截器，只控制真实查询后的线程时序，让两个请求先检查到“无审核单”，再依次完成写入。修复前任务、同年度手动绩效均生成两张有效审核单；2026 年填 7、2027 年填 5 的并发请求使数值型总值变成 5。
- 方案：复用现有事务，在任何普通查询前锁定任务或绩效主记录。直接填报、四级汇总、退回重提共享任务锁；绩效按整项加锁，使不同年度各自填报成功后仍能正确汇总。锁由事务提交或回滚释放，不增加进程内锁或新依赖。
- 重提入口：旧审核单也采用当前读，再锁任务，避免 MySQL 可重复读隔离级别在等待任务锁之前建立旧快照。活跃单检查保留原 SQL，避免为空的查询范围增加间隙锁。
- 改动文件：`BizMapper`、`PerformanceMapper` 各新增专用锁定查询；`BizService` 的三类提交入口与 `PerformanceService.submitPref` 使用这些查询。原有读取接口不变。
- 验证范围：任务直接提交、四级汇总、两类重提及不同入口交错提交；手动绩效数值/百分比并发填报、跨年度汇总；检查有效审核单、快照、日志、通知数量以及退回后实际值恢复。
- 异常闭环：在隔离库中注入写入失败，首条请求已插入的审核单和快照完整回滚，等待的第二条请求正常提交；随后退回仍恢复到初始值。临时故障触发器在测试结束时删除。
- 最终回归：累计 **21 项 HTTP + MySQL 测试全部通过，0 失败、0 错误、0 跳过**。新增并发测试覆盖 6 种任务提交组合、数值/百分比同年度与跨年度填报、任务和绩效的失败回滚两种场景。
- `mvn.cmd -B -DskipTests package` 构建通过，`git diff --check` 通过；隔离测试库已删除。本批仅验证后端接口，未执行浏览器人工测试。

## 复测与部署

在后端目录设置进程环境变量 `SHUANGGAO_TEST_DB_PASSWORD`，执行 `python scripts/run-review-regression.py`。脚本仅复制本地业务库表结构，在随机测试库内生成合成数据，通过随机端口测试真实接口，结束后删除测试库。构建命令为 `mvn.cmd -B -DskipTests package`。

本批沿用现有接口、分层和错误处理；无表结构变更、历史数据修改或新增依赖，无需迁移及回滚 SQL。部署沿用原后端 JAR 和外置配置，回滚恢复旧 JAR；代码可按各项独立提交 revert。本次不部署、不推送。
