## 18-1【中 / BUG】预算金额受 Excel 显示格式影响

- 位置：`service/BudgetService.java:360`、`:386`。
- 两份合成 Excel 的数值单元格底层均为 1.2345，分别设置显示格式 0.00 与 0.0000；导入不同月份后，资金来源金额及任务金额分别保存为 1.23 和 1.2345。
- 上传前通过 openpyxl 再读取文件，确认两份原始值相同；实际导入接口的返回结果由 Mapper 重新读取数据库生成。
- 原因：numberAt 经 DataFormatter 取得格式化显示文本，再转 BigDecimal，而非读取数值本身。数据库金额列支持 4 位小数。
- 影响：仅调整 Excel 显示位数即可改变实际保存的预算，原始金额精度丢失。
- 建议：数值单元格及数值公式按原始数值读取；文本单元格保留兼容解析；按数据库精度明确处理舍入。
- 不涉及已忽略的非法金额转零、锁定后导入覆盖，本项使用合法数字及两个不同月份。

## 18-2【高 / BUG】同一成果的通过、退回可以同时生效

- 位置：`service/AchievementService.java:274`、`:284`；`mapper/AchievementMapper.java:98`。
- 同一合成待审成果，同时发出通过与退回请求，两次真实 HTTP 都返回成功；数据库同时新增 10→30 的 pass 日志和 10→-10 的 reject 日志，提交人同时收到“成果已归档”和“成果已退回”通知。本次最终状态为 30。
- 复现方式：独立 MySQL 事务先持有该审核单行锁，两个 HTTP 请求均真实读取状态 10 后阻塞在更新；通过 information_schema 确认两条请求均处于该隔离库 LOCK WAIT 后释放行锁。不修改服务返回值或业务代码。
- 原因：读取状态后缺少锁定/条件更新，无条件更新使先读到相同待审状态的请求都能继续。
- 影响：后提交的结果可能覆盖前一次审核，产生相互矛盾的审核记录和通知。
- 建议：事务内锁定审核单后重新校验状态，或按原状态条件更新并检查影响行数；只有成功推进流程的请求才能写日志及通知。
- 本批只实测成果审核，不据此断言任务/绩效审核也存在同样结果。与已修复的前端错对象竞态、并发重复“提交”是不同操作。

## 18-3【中 / BUG】删除账号未检查绩效待办，遗留失效处理人

- 位置：`service/SysService.java:367`、`:372`。
- 创建仅担任绩效审核人的合成账号 918003，提交一条绩效后审核单状态 10、处理人为 918003；管理员删除该账号成功。
- 删除后该账号凭证访问绩效待办返回 401，但数据库审核单仍处于状态 10，current_handler_id 仍指向该已删除账号。
- 原因：删除检查仅查询 biz_task 中负责人、归口人、审核人引用，未查询绩效配置及待处理审核单。
- 影响：绩效待办遗留不可用处理人，原审核人不能继续处理。现有绩效管理员可代审，因此不声称该单据完全无法恢复。
- 建议：删除前检查绩效责任关系及活动审核单，有引用则要求先转交；如支持自动转交，明确目标人员后在事务内完成。
